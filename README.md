# vnm — vpn-node-manager

Базовый слой VPN-ноды: одна программа, которая на уровне ядра решает, куда уходит трафик
сервера и кого к нему не пускать, — независимо от того, какие VPN-сервисы на нём крутятся
(Xray/Remnawave, AmneziaWG, TrustTunnel и что угодно ещё).

## Зачем

VPN-сервисы на ноде ничего не знают друг о друге, и правила «куда можно ходить» у каждого
свои — или их нет вовсе. Типичная дыра: в профиле Xray российские сайты заблокированы, а
клиенты AmneziaWG ходят на них напрямую с IP ноды. vnm закрывает это один раз, для всего
сервера:

- **Политика назначений (egress).** Списки адресов и доменов из конфига → действие:
  отправить через выход (например, Cloudflare WARP), заблокировать или выпустить напрямую.
  Работает для любого трафика: процессов самой ноды, контейнеров и клиентов туннелей.
- **Выход WARP.** Своя регистрация Cloudflare WARP на каждой ноде, проверка здоровья,
  автоматический перевыпуск, если выход умер.
- **Fail-closed.** Если выход недоступен, трафик по его правилу отклоняется, а не уходит
  напрямую. Смерть агента ничего не открывает: правила остаются в ядре.
- **Guard.** Блок входящих соединений от адресов из блок-листов (сканеры, подсети
  госорганизаций) — до ufw, Docker и всех сервисов.
- **Свой DNS-резолвер** для доменных списков: адреса доменов попадают в наборы ядра в момент
  ответа, так что правило срабатывает, даже если сайт живёт не на «своих» IP.
- **Базовая настройка сервера** (по желанию): вход только по ключу, fail2ban, сетевые sysctl,
  swap.

vnm **не знает смысла списков**: «ru_ip» или «corp» — это только имена в конфиге. Что куда
отправлять, целиком задаётся в `/etc/vnm/config.yaml`.

## Как это устроено

```
                 ┌──────────────── vnm-agent ─────────────────┐
config.yaml ───▶ │ списки (скачать/проверить) → план → nftables│──▶ ядро: таблица inet vnm,
                 │ здоровье выходов, перевыпуск, метрики       │     ip rule, маршруты выходов
                 └─────────────────────────────────────────────┘
vnm-dns   — резолвер: ответы по доменам списков кладёт в наборы nftables
vnm-boot  — при загрузке восстанавливает последнее рабочее состояние с диска, до подъёма сети
vnm (CLI) — установка, переключение режимов, статус, диагностика
```

- Решение принимается один раз, на первом пакете нового соединения, и запоминается в метке
  conntrack. Ответы клиентам никогда не перенаправляются.
- Вся политика живёт в одной таблице `inet vnm`, которой владеет агент. Чужие таблицы (ufw,
  Docker, iptables других сервисов) vnm не читает и не трогает.
- Агент раз в несколько секунд сверяет ядро с планом и возвращает всё, что изменили руками
  (это считается дрейфом и видно в статусе и метриках).

### Режимы и безопасные переключения

| Режим | Что происходит |
|---|---|
| `observe` | всё классифицируется и считается, трафик не меняется — «что было бы» |
| `enforce` | рабочий режим |
| `off` | политика снята |

Выход egress из `enforce` (в `observe` или `off`) выпускает трафик списков с IP ноды, поэтому
требует явного `-allow-leak` — случайно открыть утечку командой нельзя. Egress и guard
переключаются независимо. Любое переключение можно сделать **временным**:
`-auto-rollback 5m` — если за 5 минут его не подтвердить **из новой SSH-сессии**, vnm сам
вернёт прежний режим. Так же устроена настройка SSH в base: потеряли доступ — через 5 минут
всё откатится.

## Что входит в комплект

| Что | Где на ноде |
|---|---|
| Бинарник `vnm` (статический, CLI + агент + резолвер) | `/usr/local/bin/vnm` |
| Конфиг политики | `/etc/vnm/config.yaml` (при установке кладётся `configs/vnm.yaml`, если файла нет) |
| Юниты `vnm-agent`, `vnm-boot`, `vnm-dns` | `/etc/systemd/system/` (шаблоны в `init/`) |
| Выход WARP: аккаунт и конфиг | `/etc/vnm/exits/warp/` (права 600) |
| `wgcf` (пин версии и sha256) | `/usr/local/lib/vnm/wgcf` |
| Состояние агента, кеши списков, бэкапы миграции | `/var/lib/vnm/` |
| Метрики для node_exporter (textfile) | `/var/lib/node_exporter/textfile_collector/vnm.prom` |

Установщик сам ставит нужные пакеты (`nftables`, `fail2ban` для base) и создаёт системного
пользователя `vnm-dns` для резолвера.

## Требования

- Ubuntu **22.04 / 24.04 / 26.04**, Debian **12 / 13** или AlmaLinux **9 / 10**, архитектура **amd64**. На других ОС
  установщик отказывает, ничего не меняя (Ubuntu 20.04 не поддерживается: старый nftables).
- root, systemd, ядро с WireGuard (для выхода WARP).
- Хотя бы один SSH-ключ в `authorized_keys` root, если ставится base (без ключа base откажет,
  чтобы не отрезать доступ).
- Исходящий доступ к GitHub (списки geo) и к Cloudflare (регистрация WARP).

## Сборка

```bash
make build        # bin/vnm, статический бинарник, версия = git describe
make check        # fmt + vet + тесты — обязательно перед выкаткой на ноду
make test-short   # только юнит-тесты, без network namespace
```

Полный `make test` включает стенд `test/flowstand` — настоящие правила в непривилегированных
network namespace (нужны `unshare` и `nft`, без них стенд пропускается).

## Установка на ноду

```bash
# 1. Бинарник и конфиг
scp bin/vnm root@NODE:/usr/local/bin/vnm
ssh root@NODE 'chmod 755 /usr/local/bin/vnm && mkdir -p /etc/vnm'
scp config.yaml root@NODE:/etc/vnm/config.yaml   # или без него — встанет configs/vnm.yaml

# Перед установкой впишите в exempt адреса, которые управляют нодой (панель, мониторинг):
# в configs/vnm.yaml там стоит документационный 203.0.113.10 — он никого не освобождает.

# 2. Установка: base + WARP + юниты. Режим берётся из конфига (начинайте с observe).
ssh root@NODE 'vnm install'
#   -skip-base          не трогать SSH, fail2ban, sysctl и swap
#   -license KEY        сразу применить ключ WARP+
#   -trust CIDR,…       адреса, которые fail2ban никогда не банит

# 3. Подтвердить SSH-настройку base — ИЗ НОВОЙ SSH-сессии, в течение 5 минут
ssh root@NODE 'vnm base confirm'

# 4. Проверить
ssh root@NODE 'vnm status; vnm doctor'
ssh root@NODE 'vnm test ya.ru; vnm test 1.1.1.1'   # что нода делает с назначением
```

### Включение egress и guard

```bash
ssh root@NODE 'vnm egress enforce -auto-rollback 5m'
# проверка: трафик по правилу идёт через выход, остальной — с IP ноды, сервисы живы
ssh root@NODE 'curl -s https://nplus1.ru/cdn-cgi/trace | grep warp'   # warp=on
ssh root@NODE 'vnm egress confirm'                                     # из новой сессии

ssh root@NODE 'vnm guard enforce -auto-rollback 5m'
# проверка: SSH, порты сервисов, связь с панелью
ssh root@NODE 'vnm guard confirm'                                      # из новой сессии
```

Не подтвердили — через 5 минут режим вернётся сам. Передумали раньше —
`vnm egress rollback` / `vnm guard rollback`.

### Если на сервере уже был WARP

Установщик находит ручной WARP (`wg-quick@warp`, свои `ip rule` на метку `0xca6c`, wtm),
сохраняет его в `/var/lib/vnm/migration/<дата>/`, сносит и регистрирует свой. Правило, которое
он не может однозначно отнести к старому WARP, — остановка с описанием, решение за оператором.
На время замены (1–2 минуты) трафик по правилам выхода отклоняется, остальной не затрагивается.

## Конфиг

Разделы `/etc/vnm/config.yaml` (полный пример с комментариями — `configs/vnm.yaml`):

| Раздел | Что задаёт |
|---|---|
| `mode` | режим egress: `observe` / `enforce` / `off` |
| `geo` | откуда брать `geoip.dat` / `geosite.dat` для списков вида `geoip:…`, `geosite:…` |
| `dns` | порт резолвера и вышестоящие DNS |
| `exits` | выходы: интерфейс, конфиг, запасные endpoints, проверка здоровья, команда перевыпуска |
| `lists` | списки: `ip` (geoip, `url:`, `file:`), `domain`, `suffix`, `extra_cidr`, границы размера, частота обновления |
| `policy` | правила по порядку, первое совпадение побеждает: `lists → action` (`exit:<имя>`, `block`, `direct`) + `fallback` на случай мёртвого выхода |
| `guard` | режим и правила блока входящих: `lists → drop/reject`, `log` |
| `exempt` | адреса, которые не трогают ни политика, ни guard (панель, управление) |

Пример правила:

```yaml
policy:
  - lists: [ru_ip, ru_domain, ru_suffix]
    action: exit:warp
    fallback: block
```

Конфиг читается строго: неизвестное поле — ошибка, и в силе остаётся последний валидный.
Поэтому при обновлении сначала выкатывается новый бинарник, потом конфиг с новыми полями.

## Команды

| Команда | Что делает |
|---|---|
| `vnm install [-skip-base] [-license KEY] [-trust …]` | полная установка ноды |
| `vnm base apply` / `vnm base confirm` | базовая настройка / подтвердить SSH-изменения |
| `vnm warp install` / `plus KEY` / `reissue` | регистрация WARP / ключ WARP+ / новая регистрация |
| `vnm egress observe\|enforce\|off [-allow-leak] [-auto-rollback 5m]` | режим политики назначений |
| `vnm guard observe\|enforce\|off [-auto-rollback 5m]` | режим guard |
| `vnm egress\|guard confirm\|rollback` | оставить или откатить временное переключение |
| `vnm status` | что агент увидел на последнем проходе: режимы, выходы, списки, счётчики, ошибки |
| `vnm test IP\|DOMAIN` | как нода поступит с этим назначением |
| `vnm doctor` | сквозная проверка ноды |
| `vnm lists update` | скачать списки сейчас |
| `vnm agent` / `vnm boot` / `vnm dns serve` | то, что запускают юниты |
| `vnm version` | версия сборки |

## Метрики

Агент пишет файл в формате Prometheus для textfile-коллектора node_exporter. Главное:

- `vnm_exit_healthy`, `vnm_exit_alert` — жив ли выход и не мёртв ли он дольше 15 минут;
- `vnm_policy_applied`, `vnm_drift_total`, `vnm_apply_errors_total` — стоит ли политика в ядре;
- `vnm_connections_total` — сколько соединений классифицировано каждым правилом;
- `vnm_guard_refused_total{list}` — сколько отбил guard (в observe — «отбил бы»);
- `vnm_list_entries`, `vnm_list_age_seconds`, `vnm_list_failed` — состояние списков;
- `vnm_resolver_up` — работает ли резолвер.

node_exporter в комплект не входит: чтобы метрики собирались, его нужно поставить на ноду
отдельно.

## Известные особенности

- **Монолитное ядро без `modprobe`** (образы некоторых хостеров): base падает на шаге sysctl —
  ставить с `-skip-base`, сетевые sysctl задать вручную. Там же у nft нет именованных
  счётчиков: политика работает, но `vnm status` не покажет счётчики.
- **ufw / firewalld:** установщик открывает порт резолвера (5353) и кладёт интерфейс выхода
  в зону firewalld, **если фаервол уже включён**. Включили ufw после vnm — откройте 5353 сами
  (`vnm doctor` это покажет).
- **IPv6:** выходы только IPv4. Резолвер отдаёт домены списков с выходом без AAAA, а
  литеральные IPv6-адреса из таких списков блокируются.
