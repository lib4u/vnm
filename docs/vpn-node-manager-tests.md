# vpn-node-manager — приёмочные тесты и матрица отказов

Часть ТЗ **docs/vpn-node-manager-tz.md** (установщик — docs/vpn-node-manager-installer.md). Номера инвариантов (I-1…I-6) — оттуда.
Все тесты MUST PASS; релиз с упавшим тестом не выкатывается.

## 1. Стенд модели потоков (этап 0, до кода агента)

Главный риск всей работы — перепутать инициированное соединение с ответом и завернуть в WARP
ответы клиентам: нода станет недоступна из РФ целиком. Поэтому модель потоков (§3.1 ТЗ)
проверяется **первой**, на голых правилах nft, до написания агента.

Стенд — network namespaces на одной машине (запускается в CI и руками):

```
[ru-client] ──── [inet] ──── [node] ──── [warp-peer]
 адрес из          маршрутизатор   awg-подобный интерфейс,     WireGuard-«Cloudflare»
 ru-списка         + «RU-сайт»     процесс-«xray», sshd
                   + «иностр.сайт»
```

`ru-client` и «RU-сайт» получают адреса из тестового `ru_ip`; «иностранный сайт» — вне
списка. Правила nft и маршруты — те, что будет генерировать агент (golden-файл).

| # | Сценарий | Ожидание | Инвариант |
|---|---|---|---|
| F-1 | TCP: процесс ноды → RU-сайт | SYN на `warp-peer`, на внешнем интерфейсе ноды нет | I-1 |
| F-2 | TCP: ru-client → sshd ноды, ответы | ответы уходят напрямую, сессия живёт | I-3 |
| F-3 | UDP: процесс ноды → RU-сайт | через warp | I-1 |
| F-4 | UDP: ru-client → UDP-сервис ноды, ответы | напрямую | I-3 |
| F-5 | UDP-сервер ноды шлёт ru-client **после истечения conntrack** (`conntrack -F` / ожидание таймаута) | напрямую (метка обхода; без неё — `listen_ports`) | I-3 |
| F-6 | транзит: туннельный клиент → RU-сайт | через warp, адрес источника = адрес warp | I-1 |
| F-7 | транзит: туннельный клиент → иностранный сайт | напрямую, без изменений | I-4 |
| F-8 | интернет → туннельный клиент (ответы на F-7) | доходят | I-3/I-4 |
| F-9 | TCP-ретрансмиты и долгоживущее соединение к RU-сайту | все пакеты по одному пути (ct mark) | I-1 |
| F-10 | QUIC (UDP 443) туннельного клиента к RU-сайту | через warp | I-1 |
| F-11 | QUIC клиента к ноде (hysteria-подобный сервис), ответы | напрямую | I-3 |
| F-12 | соединение к RU-сайту, установленное **до** применения правил | досылается по старому пути, новые — через warp; поведение зафиксировать | — |
| F-13 | `bind(:443)`+`connect(RU:443)` из процесса ноды | уходит напрямую (известная дыра `listen_ports`), виден счётчик `listen_port_bypass` | §3.4 |

Если хоть один из F-2, F-4, F-5, F-8, F-11 падает — модель потоков неверна, дальше не идём.

|---|---|---|---|

| A-20 | CLI и агент меняют состояние одновременно | второй ждёт `flock`, промежуточного состояния нет | I-6 |
| A-21 | сбой на середине apply (симулировать отказ netlink после nft) | rollback к last-good, verify совпадает | I-6 |
| A-22 | чужой объект изменился (сосед добавил `ip rule` 1500) | агент не трогает, только метрика `foreign_conflict` | — |
| A-23 | observe: трафик не меняется, растут `would_total{action}` | да | — |
| A-24 | нода с Xray: outbound с `sockopt.mark 51820` | продолжает уходить в WARP | I-4 |
| A-25 | CI: поиск `awg\|amnezia\|xray\|trusttunnel\|remna\|docker\|hysteria` в коде и шаблонах конфига агента | пусто (стенд и документация исключены) | §2.1 |
| A-26 | на ноде появился новый нижний интерфейс неизвестного типа (`ip link add … type dummy`/veth с клиентом за ним) | его транзит к назначениям политики уходит в выход без правки конфига агента | §2.1 |
| A-27 | миграция с ручного WARP (копия ручной раскладки на стенде: `PostUp` с `ip rule`, 1000 lookup + 1001 blackhole) | на каждом шаге installer §2.1 RU — WARP или отказ, ни одного SYN к RU с `ens3`; после — интерфейс `warp` под агентом, нет `wg-quick@warp`, wtm, ручных правил и файлов, бэкап на месте; метка Xray снова уходит в WARP | I-1/I-2 |
| A-28 | миграция на ноде с неопознанным правилом в диапазоне (`0xca6d → 51821`) | стоп до шага 2, ничего не изменено | §6.1 |

Проверка маршрута — **только по адресу назначения**: `tcpdump -ni ens3` и `-ni warp` с
`host <IP сайта> and tcp-syn`. Счётчики `wg show warp transfer` растут от чужого трафика и
ничего не доказывают. Проверка метки из процесса — **сокетом** (`setsockopt(SO_MARK)` до
`connect`), не `iptables -j MARK`: метка после выбора адреса источника даёт ложную поломку.

## 3. Матрица отказов

| Отказ | RU-назначения | не-RU | Управление | Чем держится |
|---|---|---|---|---|
| WARP: интерфейс лёг | блок | напрямую | работает | агент: `dead_exits`; без агента — маршрут исчез → правило 1001 |
| WARP: UP, но мёртв | блок (≤ 60 с) | напрямую | работает | агент кладёт выход в `dead_exits` |
| агент мёртв | как было (WARP / блок) | напрямую | работает | ядро держит last-good; I-2 — правило 1001 |
| агент мёртв + WARP лёг | блок (транзит — сразу, локальный — таймаут) | напрямую | работает | правило 1001, без агента |
| резолвер `vnm-dns` лёг | IP-список работает; домены — только уже в наборе, до TTL | напрямую | работает | набор с таймаутом |
| обновление списков падает | старый список | напрямую | работает | last-good; алерт по возрасту |
| конфиг битый | last-good | last-good | работает | validate до apply |
| сбой посреди apply | last-good | last-good | работает | rollback §7.1 |
| ребут | блок до WARP, затем WARP | напрямую | работает | `vnm-boot` до network-pre |
| регистрация WARP не удалась | блок | напрямую | работает | правило 1001 |

## 4. Откаты

| Что | Как |
|---|---|
| установка | `vnm uninstall --allow-leak` (снимает egress/dns, base/warp — по флагам) |
| enforce | `--auto-rollback` / `vnm egress rollback` |
| версия агента | предыдущий бинарь в `/var/lib/vnm/bin.prev`, `vnm self rollback` |
| конфиг | last-good в `/var/lib/vnm/last-good/` |
| списки | предыдущие в `/var/lib/vnm/lists.prev/` |
