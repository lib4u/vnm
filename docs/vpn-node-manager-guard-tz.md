# vnm guard — блок входящих из блок-листов (ТЗ)

Дополнение к `docs/vpn-node-manager-tz.md`. Источник идеи — `dotX12/traffic-guard` (ставится на
отдельные серверы): сканеры и подсети госорганизаций не должны достучаться до ноды
вообще, ни до одного порта, ни до одного сервиса, включая докер. Делаем это общим правилом
`vnm`, а не отдельным скриптом.

## 0. Что берём у traffic-guard и что нет

| traffic-guard | vnm guard |
|---|---|
| ipset `hash:net` + цепочка `SCANNERS-BLOCK` в `INPUT` | наборы в нашей таблице `inet vnm`, базовая цепочка в `prerouting` |
| докер не покрыт (нужен ручной `DOCKER-USER`) | покрыт: фильтр стоит до DNAT |
| списки один раз при установке, обновления нет | обновление по расписанию, как у geo |
| URL'ы в командной строке | списки в `config.yaml`, ничего не захардкожено |
| iptables-save / before.rules / 4 юнита | замена таблицы одной транзакцией + `vnm-boot`, как у всей политики |
| лог в файл + CSV с whois каждые 10 с | счётчики по спискам + лог в журнал с лимитом; whois — нет (§6) |

## 1. Цель и инварианты

- **G-1.** Новое входящее соединение с аплинка от адреса из блок-листа не доходит ни до
  одного процесса ноды, ни до контейнера за DNAT.
- **G-2.** Guard не трогает ответы: соединение, которое открыла сама нода или её клиент, не
  ломается, даже если удалённая сторона в блок-листе.
- **G-3.** Guard никогда не режет `exempt` (панель, управление) — анти-самоблок.
- **G-4.** Отказ guard (списки не скачались, битый источник) никак не влияет на egress-политику
  (RU → WARP): это независимые части. И наоборот, `vnm egress off` не снимает guard.
- **G-5.** Трафик клиентов из туннелей (`iifname` не аплинк) guard не фильтрует: он про
  входящие из интернета.

## 2. Конфиг

Списки задаются в том же разделе `lists:`, источники — существующие `url:`, `file:`,
`extra_cidr`. Новое — два поля списка и раздел `guard`.

```yaml
lists:
  - name: antiscanner
    ip: ["url:https://raw.githubusercontent.com/shadow-netlab/traffic-guard-lists/refs/heads/main/public/antiscanner.list"]
    checksum: none            # источник не публикует .sha256sum (§3.2)
    refresh: 12h              # как часто качать; по умолчанию 24h
    bounds: { min: 50, max: 5000, max_change: 0.5 }
  - name: gov_networks
    ip: ["url:https://raw.githubusercontent.com/shadow-netlab/traffic-guard-lists/refs/heads/main/public/government_networks.list"]
    checksum: none
    refresh: 24h
    bounds: { min: 2000, max: 50000, max_change: 0.3 }
  - name: skipa               # сканеры «СКИПА»: ГРЧЦ AS61280, «Спутник» AS197571 …
    ip: ["url:https://raw.githubusercontent.com/shadow-netlab/traffic-guard-lists/refs/heads/main/public/skipa.list"]
    checksum: none
    refresh: 24h
    bounds: { min: 50, max: 5000, max_change: 0.5 }
  - name: guard_manual        # ручные баны оператора
    ip: ["file:/etc/vnm/guard-manual.list"]

guard:
  mode: observe               # observe | enforce | off — независимо от mode (egress)
  rules:
    - lists: [antiscanner, skipa, gov_networks, guard_manual]
      action: drop            # drop | reject
      log: true               # §6
```

Валидация:
- `checksum: none` без `bounds` — ошибка конфига: без суммы только границы отличают список
  от страницы ошибки или обрезанного файла.
- `refresh` ≥ 1h.
- Список в `guard.rules` должен иметь адресные источники: доменные для входящих бессмысленны,
  ошибка валидации.
- Один список может стоять и в `policy`, и в `guard` — тогда действует строгость egress
  (§3.3).
- `guard.mode` по умолчанию `off`: раздел без `mode` ничего не режет, пока его не включили
  явно.

## 3. Списки и обновления

### 3.1. Расписание

- **Срок — у копии, не у таймера.** Копия скачивается, когда она старше `refresh` своего
  списка (у файла, который читают несколько списков, — самого короткого) плюс сдвиг ноды:
  доля до 10 % от `refresh`, выбранная случайно при старте агента, чтобы парк не качал разом.
  Агент раз в 10 мин проверяет, какие копии «к сроку». Неудачная загрузка повторяется с
  паузой: 10 мин, дальше ×2, не реже раза в `refresh` источника — источник, который стабильно
  не сходится по сумме, не качается гигабайтами. Расписание переживает рестарт: оно выводится
  из времени последней проверки копии (отдельно от времени изменения её содержимого).
  Прежние общие «сутки + до 6 ч» убраны.
- Подтверждение копии (304 или совпавшая сумма) не считается изменением: списки перечитываются
  только при новом содержимом; правка `file:`-источника тоже замечается.
- Скачивание — в фоне (агент не останавливает проверки выходов). Агент сам замечает любые
  обновлённые копии, `vnm lists update` качает всё сразу, не глядя на срок.
- Условный GET (`If-None-Match` по сохранённому ETag): неизменившийся файл не качается
  заново, но возраст копии обновляется (она подтверждена актуальной).

### 3.2. Целостность без контрольной суммы

`checksum: sha256sum` (по умолчанию) — как сейчас, сверка с `<файл>.sha256sum`.
`checksum: none` — источники, которые сумм не публикуют (raw.githubusercontent):
- только HTTPS; редирект на другой хост — отказ;
- **строгий разбор всего файла**: каждая непустая строка без комментария — CIDR или адрес,
  иначе файл отвергается целиком (HTML-страница ошибки). Обрезка на середине строки
  (`…/24` → `…/2`) ловится тем, что передача доказала полноту — тело совпало с
  `Content-Length` или пришло в gzip с проверкой хвоста; без этого последняя строка обязана
  кончаться переводом строки (у antiscanner и skipa его нет). Диапазон с битами хоста
  маскируется, как его читает nft: в реальных списках такие есть (`195.182.151.212/29` в
  government_networks). `::ffff:a.b.c.d` приводится к IPv4;
- файл без единой записи отвергается;
- редирект: на каждом шаге только https и тот же хост (у источников с sha256 хост может
  смениться — release-файлы GitHub, — схема нет);
- прошло — атомарная подмена копии; нет — старая копия остаётся, WARN + метрика;
- `bounds` обязательны (min/max/max_change) и проверяются при разрешении списка, как у всех
  списков: обрезка по границе строки ловится здесь. Копия к этому моменту уже заменена, но
  список в силе остаётся прежним (§3.3).
- Оператор может закрепить версию: raw-URL на конкретный коммит вместо `refs/heads/main`.

### 3.3. Отказ списка

- Egress-списки — как сейчас: без разрешённого списка политика не планируется (I-1, утечка
  хуже простоя).
- Строгость — по использованию в **активных** частях: список активного egress строгий,
  список только guard — мягкий. Списки, которые ни одна активная часть не применяет, не
  разрешаются вовсе (но скачиваются — готовы к включению).
- Guard-списки — **fail-open по одному списку**: не разрешился впервые → его наборы пустые,
  правило по нему ничего не режет, ERROR в журнал, `vnm_list_failed{list}` и FAIL в `doctor`.
  Разрешался раньше, а его определение в файле не менялось (правки остального файла, вроде
  `vnm guard enforce`, не в счёт) → в силе остаются прежние диапазоны, WARN. Остальные списки
  guard и вся egress-политика работают.
- После рестарта агент берёт размеры списков в силе из last-good: `max_change` (по каждому
  семейству отдельно) действует и для первой копии после перезапуска.
- Список в обоих разделах подчиняется правилу egress.

## 4. Ядро

Всё в таблице `inet vnm`, замена одной транзакцией по описи (наборы резолвера и счётчики,
включая `g_*`, переживают замену), как у остальной политики:

```
set l_<list>_4 { type ipv4_addr; flags interval; }  # те же наборы, что у egress-списков
set l_<list>_6 { type ipv6_addr; flags interval; }

chain guard {
	type filter hook prerouting priority -160; policy accept;
	iifname != @uplinks return                          # G-5
	ct state != new return                              # G-2
	ip saddr @exempt4 return                            # G-3
	ip6 saddr @exempt6 return
	ip saddr @l_gov_networks_4 limit rate 10/minute burst 20 packets log prefix "vnm-guard gov_networks: "
	ip saddr @l_gov_networks_4 counter name g_gov_networks_4 drop
	…
}
```

`limit` стоит в отдельном правиле без вердикта: в одном правиле с `drop` превышение лимита
отменило бы и сброс. `reject` — переход в `guard_reject` (TCP RST, иначе ICMP
admin-prohibited). Список в обоих разделах — один набор на оба.

- **Приоритет −160:** после conntrack (−200) — нужен `ct state`; до классификации (−150)
  и до DNAT (−100) — покрывает `INPUT`, докер-порты за DNAT и форвард одной цепочкой, без
  `DOCKER-USER`.
- **Почему не stateless в raw:** в raw нет состояния, и ответы на исходящие соединения ноды
  из этих сетей тоже бы резались (нарушение G-2).
- `drop` по умолчанию: сканер не получает даже RST, порт выглядит несуществующим. `reject` —
  по желанию.
- Режим `observe`: то же правило со счётчиком, без `drop` («would drop»), как egress observe.
- Наборы собираются через `NormalizePrefixes` (слияние перекрытий); 13 тыс. префиксов для
  interval-набора — штатный размер (у `ru_ip` 25 тыс.).
- Анти-самоблок — `exempt`: он общий для обоих направлений (панель, управление). Адреса
  `-trust` установщика туда не попадают сами: оператору, чья сеть в гос-списках, их нужно
  вписать в `exempt`.

Планировщик: `netstate.State` получает `Guard`. Egress и guard планируются независимо:
`mode: off` оставляет в таблице наборы, `exempt`, аплинки и guard, но ни одной цепочки,
трогающей метку соединения (классификация рисуется только при наличии решений). Состояние
last-good прежних версий читается как есть: новое поле пустое, старые цепочки на месте.

## 5. CLI

- `vnm guard observe|enforce|off [-auto-rollback 5m] | confirm | rollback` — общий с
  `vnm egress` переключатель (`modeswitch`): правится одно значение (`guard.mode`) байт в
  байт, бэкап в `/run/vnm/mode-previous.yaml`, таймер `vnm-mode-rollback`. Одно временное
  переключение за раз на обе части: откат возвращает файл целиком. Понижение guard согласия
  не требует — рискованное направление здесь повышение, его и страхует автооткат.
- `vnm test <ip>` — строка `inbound from it ⇒ DROP (list …)` / `REJECT` / `ALLOW (exempt)` /
  `ALLOW (guard observe; …)`.
- `vnm status` — режим guard, сбросы по спискам, по строке на каждый список (диапазоны,
  возраст копий, refresh, сбой разрешения).
- `vnm doctor` — по каждому применяемому списку: без копии или guard-список, не
  разрешившийся ни разу → FAIL; копии старше `3 × refresh` → WARN, `7 × refresh` → FAIL;
  guard в `observe` → WARN (длительность observe агент не хранит).

## 6. Логи и метрики

- `vnm_guard_refused_total{list}` и `vnm_guard_mode{mode}`: в observe счётчик значит «было бы
  отказано». Считаются **пакеты** новых соединений: отказанное соединение не
  устанавливается, и каждый повтор SYN — снова «новый». Метки — только имена списков.
- `log: true` — `log prefix "vnm-guard <list> "` с `limit rate 10/minute burst 20` **на
  правило** (не на IP): журнал ядра не затопит при сканировании /0. Per-IP лимит (nft
  `meter`) — отдельная задача, если понадобится.
- Whois/ASN-агрегация traffic-guard (CSV каждые 10 с) не переносится: это аналитика, не
  защита. При необходимости — отдельный разбор журнала (`journalctl -k -g vnm-guard`).
- По спискам: `vnm_list_entries{list}`, `vnm_list_age_seconds{list}` (`+Inf` без копии),
  `vnm_list_refresh_seconds{list}`, `vnm_list_failed{list}`. Прежний общий
  `vnm_list_age_seconds` без метки убран.

## 7. Соседи

- **fail2ban** остаётся: он банит по логам sshd, guard — по спискам. Не пересекаются.
- **UFW/iptables:** guard стоит раньше в `prerouting` и ничего в них не меняет.
- **TrafficGuard на существующих серверах** (сервер управления и т. п.): установщик находит `SCANNERS-BLOCK`,
  ipset `SCANNERS-BLOCK-V4/V6`, юниты `antiscan-*`, блок в `/etc/ufw/before.rules` и
  `after.rules` (DOCKER-USER). Снимает их только после того, как guard стал `enforce` и
  прошёл проверку (как миграция WARP), с бэкапом в `/var/lib/vnm/migration`. На сервер
  управления — только отдельным решением владельца.

## 8. Тесты

- **Планировщик/рендер:** golden-правила guard в enforce/observe/off; `egress off` +
  `guard enforce` даёт таблицу только с guard; валидация (`checksum: none` без bounds,
  доменный список в guard, `refresh` < 1h).
- **listcache:** `checksum: none` — HTML вместо списка отвергнут целиком, обрезанная строка
  отвергнута, bounds, условный GET (304 обновляет возраст, не качает).
- **Агент:** guard-список без копии не мешает egress-плану; по-списочные сроки обновления.
- **Стенд модели потоков** (новые сценарии):
  - G-1: источник из списка → TCP к порту ноды: timeout (нет SYN-ACK);
  - G-1d: то же к порту за DNAT (контейнер-заглушка в netns) — timeout;
  - G-2: нода открывает соединение к адресу из списка — ответ доходит;
  - G-3: адрес из `exempt`, попавший в список, — проходит;
  - G-5: клиент из нижнего интерфейса к адресу из списка — не затронут guard;
  - G-6: observe — проходит, счётчик растёт;
  - G-7: egress off + guard enforce — G-1 держится.
  Все прошли на ядре 27.09.2026 (плюс G-0/G-0d — контроль: не-списочный источник доходит до
  ноды и до контейнера за DNAT; G-1u — UDP).
- **Пилот:** одна нода, `observe` на сутки (смотрим счётчики: ожидание — сотни/тысячи
  попыток в сутки, по опыту сервера управления) → `enforce -auto-rollback 5m` → confirm.

## 9. Этапы

1. ✅ Списки: `checksum`, `refresh` по-списочно, условный GET, по-списочные возраст/метрики.
2. ✅ Guard: домен (конфиг, валидация), планировщик, рендер, счётчики.
3. ✅ CLI: `vnm guard`, `test`/`status`/`doctor`.
4. ✅ Стенд G-0…G-7; пилот на одной ноде — в работе.
5. Миграция с TrafficGuard (по команде — на сервер управления).

## 10. Открытые вопросы

Размер списков на 27.09.2026: antiscanner 164 префикса, skipa 144 (сканеры «СКИПА», частично
пересекаются с antiscanner), government_networks ~12,8 тыс. строк; обновляются редко
(последние коммиты — 31.05 и 05.09.2026), поэтому суточного `refresh` достаточно.

- Нужна ли whois-аналитика по сброшенным (как CSV у traffic-guard) или хватит счётчиков
  по спискам.
- Блокировать ли и **исходящие** к этим сетям — сейчас нет: исходящими управляет egress-
  политика, а гос-сети и так в `geoip:ru` → уходят через WARP.
