# vnm log — общая механика журнала событий (ТЗ)

Дополнение к `docs/vpn-node-manager-tz.md` и `docs/vpn-node-manager-guard-tz.md`. Сейчас пишет в
журнал только guard (`log prefix "vnm-guard <list>: "` в журнал ядра, §6 guard-ТЗ), у egress —
только счётчики `r<N>_<list>_<family>`, резолвер и агент в штатном режиме молчат. Этого не
хватает для разбора: видно «58 соединений ушло в выход», но не видно, куда и по какому правилу.

Нужна одна механика для всех мест, где vnm принимает решение, и флаг `log` у каждой позиции
конфига. vnm по-прежнему ничего не знает о смысле списков: журнал оперирует позициями
(`policy[0]`, `guard.rules[1]`, `exits[warp]`) и именами списков из конфига.

## 1. Инварианты

- **L-1. Журнал не влияет на трафик.** Лог — побочный эффект правила, не его условие. Отказ
  журнала (NFLOG недоступен, диск полон, читатель упал) не меняет ни одного решения и не
  переводит политику в ошибку: агент поднимает метрику и пишет одно предупреждение.
- **L-2. По умолчанию выключено.** Нет поля `log` — позиция не пишет ничего. Исключение — события
  самого агента (§3.4): их мало, и без них не разобрать ни одной аварии.
- **L-3. Объём ограничен на каждом уровне:** лимит в ядре на позицию, агрегация в агенте,
  общий потолок строк в минуту, ротация хранилища (§4). Сканирование /0 или торрент-клиент за
  нодой не должны ни забить диск, ни заметно нагрузить CPU.
- **L-4. Минимум данных о людях.** Egress-события не содержат адреса источника (адрес клиента
  туннеля или контейнера — это идентификация пользователя): только класс источника
  (`local`/`forward`) и входной интерфейс. У guard источник пишется — это внешний сканер.
- **L-5. Логи не покидают ноду** в этой версии: ни отправки, ни экспорта. Центральный сбор —
  отдельная задача (§10).
- **L-6. Совместимость:** существующий `guard.rules[].log: true` сохраняет смысл, меняется только
  транспорт (§4.1).

## 2. Позиции и что пишет каждая

| Позиция (флаг) | Событие | Когда | Что в строке |
|---|---|---|---|
| `policy[i].log` | `egress` | новое соединение совпало с правилом `i` | список, действие (`exit:<name>`/`block`/`direct`), назначение, порт, протокол, домен (если известен), класс источника |
| `policy[i].log` | `dns_match` | резолвер положил адреса домена в набор списка, который использует правило `i` | домен, список, адреса, TTL |
| `guard.rules[i].log` | `guard` | новое входящее от адреса из списка отказано (или было бы — observe) | список, действие, **источник**, порт назначения, протокол |
| `exits[j].log` | `exit_reject` | соединение отказано, потому что выход `j` мёртв (`fallback: block`, набор `dead_exits`) | выход, правило, назначение |
| — (всегда) | `agent` | смена режима, применение/ошибка/дрейф, обновление списка, здоровье выхода, перевыпуск, резолвер up/down | тип, итог, детали |

Правило, совпадение которого залогировано, логирует и доменные совпадения своих списков — так
в журнале видно не только `77.88.44.242`, но и `ya.ru`, без отдельного флага у резолвера и без
лога всех DNS-запросов подряд (запросы, не попавшие ни в один список, не пишутся никогда).

Решение «никакое правило не совпало → direct» не логируется: это весь остальной трафик ноды.

## 3. Конфиг

### 3.1. Флаг позиции

`log` — либо `true`, либо объект с переопределением лимитов позиции:

```yaml
policy:
  - lists: [ru_ip, ru_domain, ru_suffix]
    action: exit:warp
    fallback: block
    log: true                          # лимиты из раздела logging
  - lists: [corp_direct]
    action: direct
    log: { rate: 2/minute, burst: 5 }  # редкое правило, пишем мало

guard:
  mode: enforce
  rules:
    - lists: [antiscanner, skipa, gov_networks]
      action: drop
      log: true

exits:
  - name: warp
    # ...
    log: true                          # exit_reject, пока выход мёртв
```

### 3.2. Раздел `logging` (весь необязательный)

```yaml
logging:
  group: 3131          # NFLOG group; 0 = только журнал ядра (§4.1)
  rate: 10/minute      # лимит в ядре на позицию по умолчанию
  burst: 20
  window: 60s          # окно агрегации (§4.2)
  max_lines: 600       # общий потолок строк в минуту; сверх — одна строка «suppressed N»
  retention: 7d        # ОБЯЗАТЕЛЬНО, если хоть у одной позиции log включён (§4.3)
  max_size: 500MB      # потолок места под журнал событий; что наступит раньше — срок или размер
  file: ""             # пусто = только journald; путь = ещё и JSONL-файл (§4.3)
  file_max: 50MB       # размер одного файла до ротации
```

**Срок хранения задаётся только явно.** Умолчания нет: если хотя бы у одной позиции включён
`log`, а `logging.retention` не указан, конфиг невалиден (последний валидный остаётся в силе,
как при любой ошибке конфига). Так срок, в течение которого на ноде лежат сведения о
соединениях, всегда виден в конфиге и не зависит от настроек journald конкретной ОС.
Диапазон: `1h`…`90d`. `max_size` — необязательный, по умолчанию 500 МБ.

### 3.3. Схема и выкатка

- Версия схемы остаётся `1`: поля добавочные. Но конфиг читается строго (`KnownFields(true)`),
  и старый бинарник **отвергнет** конфиг с `log` в `policy`. Порядок выкатки: сначала бинарник на
  ноду, потом конфиг. `vnm install` и агент проверяют, что понимают конфиг, до замены.
- Валидация: `rate` — `N/second|minute|hour`, `burst ≥ 1`, `window` 10 с…10 мин, `max_lines ≥ 10`,
  `group` 1…65535 и не занята другим слушателем (doctor, §6).

### 3.4. События агента

Всегда пишутся в journald через `slog` (как сейчас), но с полем `event=agent` и `kind`:
`mode_switch`, `apply_ok`/`apply_error`, `drift`, `list_refresh` (ок/ошибка/отказ по `bounds`),
`exit_health` (переход healthy↔dead, с длительностью), `exit_renew`, `resolver`. Повторяющаяся
ошибка схлопывается: первая строка сразу, дальше не чаще раза в 10 минут со счётчиком.

## 4. Как устроено

### 4.1. Ядро

- В цепочке `decide` (egress) перед правилом с `log` ставится
  `<match> limit rate <rate> burst <burst> packets log group <group> prefix "<id>"`. Правило
  срабатывает только на первом пакете нового соединения (цепочка уже устроена так), поэтому
  нагрузка — одна запись на соединение, а не на пакет.
- В `guard` — то же вместо нынешнего `log prefix`. В `reject_forward`/`output` для
  `@dead_exits` — `exit_reject` той же конструкцией.
- `<id>` — позиция и поколение применённого состояния: `vnm:<gen>:p0:ru_ip:4`
  (`p`=policy, `g`=guard, `x`=exit; список; семейство). Поколение нужно, чтобы после
  перезагрузки конфига строка не была приписана чужому правилу, сменившему номер. Длина
  префикса ограничена ядром (NFLOG — 64 байта), имена длиннее обрезаются, в журнал пишется
  полное имя из таблицы соответствий агента.
- **NFLOG доступен** на обоих типах ядер парка: на Ubuntu 24.04/26.04 — модуль
  `nfnetlink_log`, на монолитных ядрах части хостеров — встроен (проверено 29.09.2026 по
  `/proc/net/netfilter/nf_log`). На таких ядрах у nft нет именованных счётчиков (`nft_objref`), так
  что журнал там станет единственной видимостью egress.
- **Нет NFLOG** (или `group: 0`) → откат на `log prefix "<id> "` в журнал ядра, как сейчас у
  guard. Агент читает его из журнала ядра (`journalctl -k` / kmsg) тем же разборщиком; doctor
  предупреждает.

### 4.2. Агент

- Подписка на NFLOG-группу через netlink (кандидат — `github.com/florianl/go-nflog`; решить
  до начала работ, §10). Из пакета берутся адреса, порты, протокол, интерфейсы; из префикса —
  позиция.
- **Домен:** резолвер при добавлении адресов в набор кладёт `addr → (domain, list, ttl)` в общий
  кеш с ограничением размера (LRU, 64k записей); агент подставляет домен в `egress`, если
  адрес там есть. Имя берётся только из ответов, попавших в наборы списков (L-4).
- **Агрегация:** ключ `(позиция, действие, назначение, порт)` в окне `window`. Первая строка —
  сразу, повторы считаются, в конце окна — одна строка с `count`. Общий потолок `max_lines`:
  сверх него события только считаются, раз в минуту — строка `suppressed N`.
- **Observe:** события помечаются `observe: true`, действие — «было бы» (`would_exit`,
  `would_drop`), как у счётчиков.

### 4.3. Куда пишется

- **journald, отдельный namespace `vnm`** (по умолчанию). Ротация основного журнала общая на
  всю систему, и `retention` через неё не выразить, не задев чужие логи. Поэтому события
  (`egress`, `guard`, `exit_reject`, `dns_match`) агент пишет по нативному протоколу в сокет
  namespace `/run/systemd/journal.vnm/socket` (systemd ≥ 245 — есть на всех поддерживаемых ОС:
  Ubuntu 22.04+ и AlmaLinux 9). Установщик кладёт `/etc/systemd/journald@vnm.conf` с
  `MaxRetentionSec=<retention>`, `SystemMaxUse=<max_size>`, `Storage=persistent` и
  `RateLimitIntervalSec=0` (наш потолок уже стоит, журнал не должен молча резать строки);
  агент при смене `retention`/`max_size` переписывает файл и перезапускает
  `systemd-journald@vnm`. Операционные логи агента (`event=agent`, §3.4) остаются в основном
  журнале — они нужны вместе с остальной системой при разборе аварии и персональных данных не
  содержат. Читать события: `journalctl --namespace=vnm` или `vnm log`.
- **Файл** (`logging.file`): JSON Lines, ротация по `file_max`, права `0640 root:adm`. Агент
  удаляет ротированные файлы старше `retention` и самые старые при превышении `max_size`
  (суммарно по всем файлам). Нужен там, где journald урезан или в памяти.
- **Откат на журнал ядра** (нет NFLOG, §4.1) — единственный случай, где срок не наш: строки
  `log prefix` пишет ядро в основной журнал, и живут они по его ротации. doctor выводит это
  WARN'ом с фактическим сроком основного журнала.

### 4.4. Формат строки

```json
{"ts":"2026-09-29T19:41:02Z","event":"egress","pos":"policy[0]","list":"ru_domain",
 "action":"exit:warp","proto":"tcp","dst":"87.240.132.72","dport":443,"domain":"vk.com",
 "src_class":"forward","iif":"awg0","gen":17}
{"ts":"2026-09-29T19:42:02Z","event":"egress","pos":"policy[0]","list":"ru_domain",
 "action":"exit:warp","dst":"87.240.132.72","dport":443,"domain":"vk.com","count":214,"window":"60s"}
{"ts":"2026-09-29T19:43:10Z","event":"guard","pos":"guard.rules[0]","list":"gov_networks",
 "action":"drop","src":"198.51.100.23","proto":"tcp","dport":443}
{"ts":"2026-09-29T19:50:00Z","event":"exit_reject","exit":"warp","pos":"policy[0]",
 "dst":"77.88.44.242","dport":443,"reason":"exit_down"}
{"ts":"2026-09-29T19:50:00Z","event":"agent","kind":"exit_health","exit":"warp",

```

## 5. CLI

- `vnm log [-f] [-since 1h] [-event egress|guard|exit_reject|dns_match|agent] [-pos policy[0]]
  [-list ru_ip] [-dst <addr|domain>] [-json]` — чтение из journald/файла с фильтрами; по
  умолчанию человекочитаемый вывод, одна строка на событие.
- `vnm status` — строка `log`: где включено (`policy[0], guard.rules[0], exits[warp]`),
  транспорт (`nflog group 3131` / `kernel log`), подавлено за час.
- `vnm log top [-since 1h] [-pos …]` — топ назначений/доменов/источников guard по счётчикам
  событий (без хранения отдельной статистики).

## 6. Doctor и метрики

- doctor: NFLOG-группа доступна и не занята другим процессом (ulogd и т. п.); при откате на
  журнал ядра — WARN с фактическим сроком основного журнала; `journald@vnm.conf` совпадает с
  `retention`/`max_size` из конфига, `systemd-journald@vnm` активен, самая старая запись
  namespace не старше `retention` (+1 сутки на ротацию журнала); права, место и срок файлов
  `logging.file`.
- Метрики (в тот же textfile): `vnm_log_events_total{pos,event}`,
  `vnm_log_suppressed_total{reason}` (`kernel_limit` не видно — это лимит ядра; `max_lines`,
  `reader_lag`), `vnm_log_transport{kind="nflog|kernel|off"}`, `vnm_log_reader_up`.

## 7. Тесты

- Юнит: разбор `log: true` / объекта / отсутствия; валидация лимитов; `log` без
  `logging.retention` → конфиг невалиден, `retention` вне `1h…90d` → невалиден; генерация
  `journald@vnm.conf` из `retention`/`max_size`; чистка файлов старше срока и сверх размера; рендер (строка `log group`
  стоит перед правилом нужной позиции, в observe — тоже); кодирование и разбор префикса с
  поколением; агрегация и потолок; откат на `log prefix` при `group: 0`.
- Flowstand (netns, `test/flowstand`): соединение к адресу из списка → событие с верными
  `pos/list/action`; доменный список → `domain` в `egress`; мёртвый выход → `exit_reject`;
  guard observe/enforce; перезагрузка конфига со сдвигом номеров правил → старые строки не
  приписаны новым позициям; 10k соединений за секунду → строк не больше потолка, счётчик
  `suppressed` сходится.
- Живая проверка на одной ноде (пилотная, как для guard): включить `log` у `policy[0]` в observe,
  сутки — объём журнала и CPU агента; затем enforce.

## 8. Этапы

1. Раздел `logging` (с обязательным `retention`), флаг `log` у `policy`/`guard`/`exits`, рендер
   `log group`, NFLOG-читатель, namespace journald `vnm` со сроком и потолком, агрегация и
   потолок строк; перевод guard на общий транспорт. Метрики.
2. Домены из кеша резолвера, `dns_match`.
3. CLI `vnm log` / `vnm log top`, строка в `status`, doctor.
4. Файловый приёмник с ротацией.

## 9. Что не делаем

- Лог всех DNS-запросов и всего трафика вне списков.
- Адрес источника в egress-событиях (L-4) — только по отдельному решению владельца (§10).
- Whois/ASN-обогащение (как в guard-ТЗ §6 — это аналитика, не журнал).
- Отправку логов с ноды.
