# ТЗ: vpn-node-manager (vnm) — базовый слой VPN-ноды и политика назначений на уровне сети

Статус: черновик r2, 27.09.2026 (учтено внешнее ревью). Код не начат.
Приёмочные тесты и матрица отказов — **docs/vpn-node-manager-tests.md** (часть ТЗ).

## 0. Цель

Сейчас RU-назначения режет или уводит **Xray** — правилами конфиг-профилей Remnawave
(`geoip:ru`/`category-ru` → BLOCK, на части нод → WARP по метке 51820). Всё, что ходит в
интернет мимо Xray, этих правил не видит: AmneziaWG (ядро форвардит клиентский трафик
с `awg*` в `ens3`), TrustTunnel (эндпоинт сам открывает соединения), любой будущий сервис.
Такой трафик приходит на RU-назначения с публичного IP ноды. Гипотеза владельца: ноды
AWG/TT «улетают» именно поэтому. Её проверяем замером (режим `observe`, §8) до включения,
но мера нужна при любом исходе.

**Цель — не «чтобы RU-сайты работали», а чтобы RU-назначение никогда не получало публичный
IP ноды.** Если сайт не откроется через WARP (сайт режет Cloudflare), это допустимо.
Если откроется с IP ноды — это дефект.

## 1. Инварианты

Нарушение любого из них — блокер релиза. Каждый покрыт тестом в tests.md.

- **I-1.** Соединение, **инициированное** нодой или её клиентом (§3.1), к назначению из
  политики с действием `exit`/`block` никогда не уходит с публичным адресом ноды (v4 и v6).
- **I-2.** WARP недоступен → такие соединения блокируются немедленно, без очереди
  и таймаута. Никогда не уходят в `ens3`.
- **I-3.** Ответный трафик входящих соединений (клиент → нода: SSH, хендшейки и ответы
  AWG, TT, Xray, hysteria) никогда не уводится в WARP и не блокируется политикой,
  даже если адрес клиента входит в RU-список.
- **I-4.** Трафик к назначениям вне политики идёт как до установки: тот же маршрут,
  тот же адрес источника, без заметной потери скорости.
- **I-5.** Управление (SSH, агенты AWG/TT, панель → remnanode, мониторинг) доступно
  в любом состоянии `vnm`, включая падение демона, битый конфиг и недоступный WARP.
- **I-6.** Отказ любой части `vnm` (демон, DNS, обновление списков, конфиг) не ослабляет
  I-1/I-2: хуже может стать только доступность RU-назначений, но не их утечка.

## 2. Состав и роли

Один бинарь `vnm`, две роли.

| Роль | Что | Когда работает |
|---|---|---|
| **установщик** (`vnm install`, `vnm base …`, `vnm warp …`) | SSH, fail2ban, sysctl, swap, регистрация WARP (`wgcf`), установка агента | разово, руками |
| **агент** (`vnm-agent`, systemd) | политика (nft + маршруты), интерфейсы выходов (подъём, здоровье, восстановление), DNS-наполнение, сверка, списки, метрики | постоянно |

Агент **не трогает** SSH, fail2ban, sysctl, пакеты: у него нет права сломать доступ
к машине. Не входят в `vnm`: порты сервисов в ufw, установка awgd/ttd/remnanode, модуль
ядра AWG (свои рунбуки).

### 2.1. Агент не знает о сервисах

Агент ничего не знает об Xray, AmneziaWG, TrustTunnel, Remnawave, Docker и любом другом
сервисе ноды — ни в коде, ни в конфиге, ни в метриках. Сервисы приходят и уходят, а
политика должна работать для любого из них без правки агента.

- **Классификация только по фактам ядра:** направление и состояние conntrack, «пакет
  пришёл с аплинка или нет», таблица сокетов (слушающие порты), метка пакета/сокета,
  адрес назначения. Никаких имён интерфейсов сервисов (`awg*`), имён процессов, cgroup
  контейнеров, портов конкретных протоколов.
- **Аплинк** — единственное, что агент знает о топологии: интерфейс(ы) маршрута по
  умолчанию, определяются автоматически (или явно в конфиге). Всё, что пришло **не** с
  аплинка и уходит наружу, — транзит от какого-то нижнего интерфейса (туннель, бридж
  контейнеров — неважно, какой).
- **Интеграция — только через публичные контракты агента**, которые сервис реализует у
  себя, а агент не проверяет, кто именно их реализовал:
  - **метка обхода** (§3.4): сокет с этим битом метки агент не трогает;
  - **выход** — сетевой интерфейс с проверкой здоровья по URL (§4); WARP — лишь один из
    вариантов, настроенный установщиком.
  Всё, что в этом ТЗ сказано про AWG/Xray/TT, — описание окружения парка и задачи на
  стороне сервисов, а не логика агента.
- **Проверяется в CI:** в исходниках и шаблонах конфига агента нет строк
  `awg|amnezia|xray|trusttunnel|remna|docker|hysteria` (кроме тестового стенда и
  документации). Установщик от этого правила освобождён только в части WARP (installer §2).

**Поддерживаемые ОС.** MVP: Ubuntu 22.04 / 24.04 / 26.04, x86_64, ядро ≥ 5.15,
nftables ≥ 1.0, systemd ≥ 249. Второй этап: AlmaLinux 9 / 10 (в парке есть: DE, GR, PL,
BG). Не из списка → установщик отказывается, ничего не меняя.

## 3. Политика назначений

### 3.1. Какие соединения подлежат политике (модель потоков)

Решение принимается **один раз на соединение** по первому пакету и хранится в conntrack
(`ct mark`); остальные пакеты соединения берут метку из него.

Соединение **подлежит политике**, только если одновременно:
1. `ct state new` и `ct direction original` — первый пакет нового соединения, открытого
   с этой стороны;
2. источник — транзит **не с аплинка** (`iifname != @uplinks`, hook `prerouting`)
   **или** локальный процесс (hook `output`). Какой сервис стоит за нижним интерфейсом или
   процессом, агент не знает и не спрашивает (§2.1);
3. пакет не несёт **метку обхода** (§3.4) — её по контракту ставят сокеты серверов,
   которые отвечают клиентам сами (например, туннельные);
4. исходный порт не в `@listen_ports` — **страховка**, не основной признак (§3.4);
5. назначение не в `@exempt`.

Матрица (✓ — так должно быть, ✗ — запрещено). Источники описаны так, как их видит ядро;
в скобках — чем они являются в нашем парке, агент этого не различает:

| Источник | Поток | Назначение | Результат (WARP жив) | WARP мёртв |
|---|---|---|---|---|
| транзит не с аплинка (клиенты AWG, контейнеры в бридже) | новое исходящее | в списке `exit` | WARP | блок |
| транзит не с аплинка | новое исходящее | вне политики | напрямую | напрямую |
| локальный процесс (Xray, эндпоинт TT, сам хост) | новое исходящее | в списке `exit` | WARP | блок |
| локальный процесс | новое исходящее | вне политики | напрямую | напрямую |
| любой | новое исходящее | в списке `block` | блок | блок |
| входящее с аплинка (клиент, в т.ч. RU-адрес) → сервис ноды | ответы | RU-адрес клиента | напрямую ✗ WARP | напрямую ✗ блок |
| локальный сервер с меткой обхода или со слушающего порта → клиент (сервер AWG) | keepalive/роуминг после истечения conntrack | RU-адрес клиента | напрямую ✗ WARP | напрямую ✗ блок |
| SSH / агенты / панель | входящие и ответы | любой | напрямую | напрямую |
| WARP (шифрованный UDP) | контрольный + данные | endpoint Cloudflare | напрямую (exempt) | напрямую |
| транзит, который чужой policy-routing уводит в другой туннель (двойной VPN на NL) | новое исходящее | — | нода-исключение до отдельной проверки (§6) |
| DNS-резолвер `vnm` → upstream | новое исходящее | upstream | напрямую (exempt) | напрямую |

Утверждение «`ct direction original` отличает инициированное от ответного» — **гипотеза до
прогона стенда**, особенно для UDP и QUIC. Стенд (tests.md §1) — первый этап работ, раньше
основного кода.

### 3.2. Списки и действия

Не зашиваем «RU». Конфиг описывает списки назначений и действия; RU — дефолтная запись.

```yaml
# /etc/vnm/config.yaml
version: 1
uplinks: auto                                          # или [ "ens3" ]
exits:
  warp:
    type: wireguard                                    # агент знает только «WireGuard-выход»
    iface: warp
    conf: /etc/vnm/exits/warp/warp.conf                # пишет установщик (installer §2)
    endpoints: [ "162.159.192.1:2408", "162.159.192.1:500", "162.159.193.10:4500" ]
    health: { url: "https://www.cloudflare.com/cdn-cgi/trace", expect: "warp=(on|plus)" }
lists:
  ru_ip:     { ip: [ "geoip:ru" ], extra_cidr: [] }
  ru_domain: { domain: [ "geosite:category-ru" ] }
  ru_suffix: { suffix: [ "ru", "su", "xn--p1ai" ] }    # .su — решение владельца, §12
policy:
  - { lists: [ru_ip, ru_domain, ru_suffix], action: "exit:warp", fallback: block }
exempt:
  cidr: [ "203.0.113.10/32" ]  # адрес сервера управления                         # + peer-адреса выходов добавляются сами
```

- Действия: `exit:<имя>`, `block`, `direct`. У `exit` обязателен `fallback`, и он может
  быть только `block` (I-2).
- Три вида списков — три разных понятия, и это фиксируется явно: **`*_ip`** — адрес
  назначения принадлежит диапазону; **`*_domain`** — домен из каталога; **`*_suffix`** —
  домен в зоне. `.ru`-домен ≠ российская компания, RU-адрес ≠ `.ru`-домен.
- **Доменные списки на уровне сети работают только через адреса** (§5): политика
  фактически «адрес, в который резолвился домен из списка». Общий адрес CDN, в который
  резолвятся и `example.ru`, и `example.com`, попадёт под политику для обоих. Это
  сознательная семантика: ошибка в сторону «лишнее в WARP», не в сторону утечки.
- Источники: `geoip:`/`geosite:` — релизы Loyalsoldier на GitHub
  (`…/v2ray-rules-dat/releases/latest/download/{geoip,geosite}.dat`, тот же датасет, что у
  клиентов); разбор **protobuf-парсером**, не `strings`. `extra_cidr`, `file:`,
  `url:` — свои.

### 3.3. Маршрутизация

Числа (метка, таблица, приоритеты) совпадают с тем, что сейчас вручную стоит на нодах с ручным
WARP, — чтобы Xray-профили с `sockopt.mark 51820` работали без правки. Сама ручная
установка при этом **сносится** (installer §2.1), а объекты переходят во владение `vnm`:

```
priority 1000:  fwmark 0xca6c lookup 51820
priority 1001:  fwmark 0xca6c unreachable        # в ручной раскладке сейчас blackhole — заменить
table 51820:    default dev warp                 # есть, пока есть интерфейс
nft set dead_exits { 0xca6c }                    # выходы, объявленные мёртвыми
```

Мёртвый выход закрыт в два слоя (проверено стендом, tests.md §1):

- **Слой 1 — агент объявляет выход мёртвым** (§4): метка выхода попадает в набор
  `dead_exits`, и соединения к нему отклоняются **до** перенаправления — в route-цепочке
  `output` (локальные) и в `forward` (транзит): TCP reset / ICMP, клиент видит отказ
  сразу. Маршрут при этом остаётся, ruleset не переписывается — меняется один элемент
  набора. Возврат — удалением элемента после восстановления.
- **Слой 2 — без агента:** интерфейс пропал → маршрут в 51820 исчез вместе с ним →
  правило 1001 `unreachable`. Транзит получает ICMP сразу; **локальный сокет — только
  таймаут**: он выбрал маршрут до того, как метка его перенаправила, и ядро молча
  отбрасывает перенаправленный пакет. Утечки нет (I-2 соблюдён), но отказ медленный —
  это цена отсутствия агента. `fib` в хуке `output` ядро не поддерживает, так что
  проверить маршрут с меткой до отправки без агента нечем.
- `block` — `reject` в netfilter (TCP reset / ICMP admin-prohibited), без маршрута.
- **SNAT на выходе — своими правилами, для всего, что уходит в `warp`:** у локального
  процесса при метке в hook `output` источник уже выбран (адрес ноды), у транзита —
  адрес нижней подсети; без маскарада ответ не вернётся ни тем, ни другим. `masquerade`
  при `oifname` выхода в таблице `vnm`. На чужой маскарад (который сейчас случайно
  покрывает транзит AWG) агент не рассчитывает.
- **Разрешение форварда — обязанность владельца нижнего интерфейса**, не агента. Агент
  не может отменить чужой `DROP` в iptables `filter FORWARD` (базовые цепочки проходятся
  все) и не знает, кто его поставил. `vnm doctor` видит общий факт «политика FORWARD =
  DROP» и предупреждает, что транзит в выход пройдёт, только если владелец нижнего
  интерфейса разрешает его форвард на любой выходной интерфейс (awgd сейчас делает
  именно так: `-i awgX -j ACCEPT`).
- `rp_filter=2` на `warp`, MSS clamp по PMTU при `oifname "warp"` (MTU 1280).
- Метка 0xca6c = 51820 совпадает с `sockopt.mark` outbound'а WARP в Xray-профилях —
  профиль продолжает работать без правки и получает fail-closed.

- **firewalld** (AlmaLinux) форвардит только в интерфейсы своих зон и остальное отклоняет с
  `admin-prohibited`: интерфейс выхода вне зон = «unreachable» у клиентов туннелей для всего,
  что политика шлёт в выход (найдено на одной из нод 27.09.2026). Установщик добавляет интерфейсы
  выходов в зону по умолчанию (если оператор не положил их в другую), `doctor` — FAIL, если нет.

### 3.4. Метка обхода и `listen_ports`

- **Метка обхода** (`0x10000`, бит под маской, не пересекается с 51820 и занятыми в парке
  0x1–0x11) — публичный контракт агента: «пакет с этим битом политика не трогает». Кто его
  ставит, агент не знает. Реализация — на стороне сервисов, отдельными задачами в их
  бэклогах: awgd — `FwMark` на сокете AWG (сейчас ставится только при
  `fwmark_workaround`); у пакетов AWG из модуля ядра нет процесса-владельца, поэтому
  метка на сокете для них единственный точный признак.
- **`listen_ports`** — страховка на время, пока метки нет у всех серверов: набор портов из
  таблицы сокетов (tcp LISTEN + udp bound) плюс статические из конфига. Известная дыра:
  процесс, который сам делает `bind(:443)` + `connect(RU:443)`, пройдёт мимо политики.
  Это ошибка в сторону доступности, её видно в счётчике `vnm_policy_listen_port_bypass`.
  Когда метка обхода есть у всех туннельных серверов ноды, страховку можно выключить
  флагом.

### 3.5. IPv6

MVP — **только IPv4 через WARP**. Для IPv6 правило жёсткое: назначения из списков
`exit`/`block` — **всегда `block`**, пока IPv6 через WARP не реализован отдельным этапом.
Нативный v6 ноды — такой же её публичный адрес, промежуточного «как получится» нет.
Нода без v6 — правила v6 всё равно ставятся (ноль стоимости, защита на случай появления
RA). Этап 2: `ip -6 rule/route`, v6 в WARP, выбор адреса источника.

## 4. Здоровье WARP

Проверка раз в **15 с**, решение по окну:

| Признак | Здоров | Мёртв |
|---|---|---|
| интерфейс `warp` | UP | нет / DOWN |
| возраст handshake | ≤ 180 с | > 180 с |
| `GET <exit.health.url>` через интерфейс выхода, таймаут 5 с, адрес резолвится заранее (DNS в проверке не участвует) | тело совпадает с `exit.health.expect` (для WARP: `warp=(on\|plus)`) | таймаут, ошибка TCP/TLS, несовпадение |

Проверка общая для любого выхода-интерфейса: URL и ожидаемый ответ — в конфиге, строку
`warp=` агент не знает. Признак handshake — для выходов типа WireGuard (читается из ядра
по интерфейсу), у других выходов этого признака нет.

- **Здоров** = все три признака ОК. **Мёртв** = 3 неудачи подряд (≈45 с) или пропал
  интерфейс (сразу). Свежий handshake при таймауте trace = мёртв: туннель без
  интернета — тоже мёртвый туннель.
- Ответ, не совпавший с `expect` (например 403 от Cloudflare без `warp=`), = мёртв: мы не
  можем подтвердить, что трафик уходит через выход.
- Мёртв → метка выхода в `dead_exits` (§3.3, слой 1). Снятие — после **4 успешных
  проверок подряд** (≈60 с), чтобы не флапать.
- **Исключение — перезапуск агента над работающим туннелем.** Если при первой проверке
  интерфейс уже существовал и проверка прошла целиком, выход признаётся живым сразу:
  правило четырёх успехов защищает от флапа выхода, вернувшегося из мёртвых, а здесь оно
  стоило бы ~45 с отказа RU на каждом рестарте (найдено на пилоте). Выход, который
  агент создаёт сам (после ребута), по-прежнему доказывает себя четырьмя проверками.
- **Интерфейсом выхода управляет только агент** — второго контроллера (watchdog, cron,
  `wg-quick`-юнита) на ноде нет, иначе два механизма перезапускают один интерфейс по
  разным порогам и флапают. Лечение мёртвого выхода — ступенями, каждая следующая после
  3 неудачных проверок на предыдущей:
  1. переустановить peer (`wgctrl`) — заставляет новый handshake;
  2. следующий адрес из `endpoints` (часть хостеров режет 2408/udp — остальные порты
     Cloudflare принимает тот же ключ);
  3. пересоздать интерфейс из `conf`;
  4. лестница повторяется по кругу, пока выход мёртв: иначе после одного прохода выход
     навсегда остался бы на втором адресе, а третий не был бы опробован никогда. Мёртв
     дольше 15 мин — алерт `vnm_exit_alert 1`. **Перерегистрацию агент не делает никогда**:
     это смена личности выхода, операция установщика (installer §2).
- IPv6 в WARP в MVP не проверяется (§3.5).
- **Подъём выхода — агент, не systemd-юнит.** При старте агент создаёт интерфейс
  (`ip link add … type wireguard`), применяет ключ, адрес, MTU и peer из `conf`
  (формат `wg-quick`, но поддерживается только подмножество: `PrivateKey`, `Address`,
  `MTU`, `[Peer] PublicKey/Endpoint/AllowedIPs/PersistentKeepalive`; любые `PostUp`,
  `Table`, `DNS` — ошибка валидации). Агент мёртв — интерфейс в ядре продолжает
  работать; после ребута до старта агента выхода нет, и работает правило 1001 (I-2).

### 4.x. Перевыпуск учётных данных выхода (renew)

Лестница (сброс peer → следующий endpoint → пересоздание интерфейса) не помогает, когда
провайдер отозвал ключ или аккаунт: хендшейка нет вовсе. Для этого у выхода необязательный
`renew: {command, after, every}` — команда, выдающая новые учётные данные и переписывающая
`conf`. Агент о провайдере не знает: он запускает команду, когда выход мёртв и **без
хендшейка** дольше `after` (15m по умолчанию, ≥ 5m), не чаще `every` (1h, ≥ 30m), и пересоздаёт
интерфейс из нового конфига. При свежем хендшейке (ключ работает, сломано что-то другое)
команда не запускается. Для WARP команда — `vnm warp reissue`: новая регистрация wgcf,
лицензия WARP+ (сохранённая при `vnm warp plus`/`install -license`) переносится, при сбое
регистрации старый аккаунт возвращается. (WTM перевыпуска не делает — только рестарт
интерфейса cron'ом раз в 5 минут.)

## 5. DNS-наполнение доменных списков — best effort

**Доменная часть — дополнение, а не гарантия.** Гарантию I-1 даёт только IP-список;
домены добирают то, что лежит на нероссийских адресах.

- Свой резолвер — `vnm dns serve`, часть бинаря (подробно — `vpn-node-manager-dns-tz.md`;
  до 27.09.2026 это был dnsmasq ≥ 2.87 с `nftset`, что привязывало доменные списки к ОС):
  ответ на запрос домена из списка кладёт адреса в nft-набор до того, как уйдёт клиенту.
- **Записи в наборе без таймаута** (решение реализации, вместо clamp TTL из r1). Резолвер
  кладёт адрес без таймаута и не продлевает его при повторных ответах — запись с таймаутом
  истекла бы, пока у клиента ещё жив кэш ответа, и соединение ушло бы с IP ноды (I-1).
  Поэтому записи живут, пока живёт таблица, и **сохраняются** при её замене: таблица не
  удаляется, а меняется по описи одной транзакцией — цепочки и статические наборы
  пересоздаются, наборы резолвера и именованные счётчики остаются как есть (адрес,
  добавленный между чтением и заменой, не теряется). Цена — адрес, который CDN потом отдал
  другому сайту, ходит через WARP: ошибка в безопасную сторону.
- Записи geosite, текстовых списков и `suffix` проверяются как домены (метки, ≤ 253 байт);
  запись Full расширяется до домена с поддоменами — в безопасную сторону.
- Резолвер — `vnm-dns.service` (конфиг `resolver.json` пишет агент), порт из `dns.port`,
  upstream'ы из `dns.upstreams` (исключены из политики). Не открытый резолвер: запрос с
  аплинка отбрасывается и в nft, и в самом резолвере. Работает от своего пользователя
  `vnm-dns` только с `CAP_NET_ADMIN`.
- Как запросы попадают в резолвер — два общих правила в nft, без знания сервисов и без
  правки системного резолвера: **транзит** (`prerouting dstnat`) — `redirect` udp/tcp 53 для
  всего, что пришло не с аплинка и не из выхода; **процессы хоста** (`output dstnat`) — тот
  же `redirect`, кроме пакетов пользователя резолвера (`meta skuid`), иначе он спрашивал бы
  сам себя. Upstream резолвера — напрямую (в `exempt`). systemd-resolved не трогается: его
  запросы к своим upstream'ам тоже перехватываются. (Drop-in для resolved отвергнут: `DNS=`
  дописывается к списку интерфейса, а не заменяет его, и resolved шлёт запросы параллельно —
  часть ответов шла бы мимо наборов.)
- Перенаправленный DNS доставляется локально, поэтому фаервол хоста должен пускать
  `dns.port`: установщик открывает его в ufw/firewalld (dns-ТЗ §4), иначе клиенты
  туннелей остаются без DNS.
- **Перенаправление — часть здоровья** (как `dead_exits`): порт 53 в наборе `dns_ports`,
  пока резолвер отвечает (агент каждый проход шлёт ему `version.bind CH TXT` — резолвер
  отвечает сам, без upstream'ов). Резолвер упал — агент опустошает набор, DNS идёт туда, куда
  был отправлен: хост и клиенты не теряют DNS, теряется только доменная часть политики. После
  перезагрузки (`vnm-boot`) набор пуст, пока агент не увидит живой резолвер.
- Что это значит в нашем парке (контекст, не логика агента): клиенты AWG получают DNS
  1.1.1.1/1.0.0.1 открытым UDP через туннель — их запросы попадут под `dnat`; Xray с
  `domainStrategy: AsIs` без своего DoH и эндпоинт TT резолвят через систему.
- **Мимо резолвера не видно:** DoH/DoT/DoQ внутри туннеля (Secure DNS в браузере), Xray-
  профили с собственным `dns` на DoH, клиенты TT с DoH-upstream (§12). Для них работает
  только IP-список. Это записано как принятое ограничение, не как дефект.

## 6. Совместимость и владение

### 6.1. Что принадлежит `vnm`

`vnm` владеет **только** этими объектами и только их чинит при расхождении:

| Объект | Идентификатор |
|---|---|
| nft-таблица | `table inet vnm` (целиком) |
| `ip rule` | приоритеты **1000–1009** (сейчас используются 1000, 1001) |
| таблица маршрутов | **51820** |
| файлы | `/etc/vnm/`, `/var/lib/vnm/`, unit-файлы `vnm-*` |
| резолвер | `vnm-dns.service`, пользователь `vnm-dns` |
| интерфейсы выходов | `warp` (и любые из `exits`), их конфиги и ключи в `/etc/vnm/exits/` |

Всё прочее — ufw, Docker, iptables-правила awgd, чужие
`ip rule` и таблицы — **только читается**. Расхождение в чужом объекте = предупреждение
и метрика `vnm_foreign_conflict`, никогда не правка: легитимный сосед не должен воевать
с агентом. Конфликт в своём диапазоне при установке (занятый приоритет 1000–1009 или
таблица 51820 с чужим содержимым) = отказ установки с объяснением. **Исключение —
ручной WARP**: его установщик опознаёт и сносит по процедуре installer §2.1, это
плановая миграция, а не конфликт. Всё остальное в диапазоне — отказ.

Перед раскаткой — инвентаризация: на одной из нод есть ещё `fwmark 0xca6d → 51821`,
`0xca6e → 51822` с маршрутами `proto bgp` в тот же `warp` неизвестного происхождения —
выяснить, что это, до установки на неё.

### 6.2. Соседи в нашем парке

Это описание окружения для раскатки и тестов, а не знание агента: агент видит только
метки, приоритеты и таблицы как числа (§2.1).

| Что | Метка / таблица / приоритет | Поведение |
|---|---|---|
| Xray с `sockopt.mark` → WARP | `sockopt.mark` 51820 | та же схема, без правки профиля |
| Xray `DIRECT:17` | 17 | не трогаем |
| awgd `fwmark_workaround` (NL) | 0x7–0x11 → main, приоритеты 88–100 | не пересекается; бит обхода 0x10000 |
| двойной VPN NL→CZ | `from all lookup 100`, приоритет 200 | **нода-исключение** до отдельной проверки |
| Docker `FORWARD DROP` | iptables filter | транзит в выход проходит через accept'ы владельца нижнего интерфейса (awgd); без них — `doctor` видит общий факт «FORWARD = DROP» и предупреждает (§3.3) |

Xray-роутинг в профилях **остаётся** первой линией; `vnm` — слой под ним.

## 7. Агент: применение состояния

### 7.1. Порядок применения — fail-closed на каждом шаге

`prepare → validate → apply → verify → (commit | rollback)`:

1. **prepare** — собрать целевое состояние целиком в памяти: ruleset nft (текст),
   наборы, `ip rule`, маршруты, конфиг резолвера.
2. **validate** — `nft -c -f` (проверка без применения), sanity-чеки списков (§7.4),
   схема конфига.
3. **apply** в порядке, где любой промежуточный срез не нарушает I-1…I-5:
   - ставим: `ip rule 1001 unreachable` → `ip rule 1000 lookup 51820` → маршрут в 51820
     (если WARP здоров) → nft-таблица атомарно (`nft -f`, в одной транзакции с наборами) →
     резолвер;
   - снимаем (`off`/`uninstall`) — строго в обратном: nft → маршрут → правила.
   Пока нет nft-меток, правила 1000/1001 ни на что не влияют; пока нет маршрута, метка
   даёт `unreachable`, а не прямой выход.
4. **verify** — прочитать состояние обратно и сравнить с целевым.
5. Не совпало → **rollback** к последнему подтверждённому состоянию (хранится
   в `/var/lib/vnm/last-good/`), ошибка в лог и метрику.

### 7.2. Загрузка и systemd

Два юнита:
- **`vnm-boot.service`** — `Type=oneshot`, `DefaultDependencies=no`,
  `After=local-fs.target`, `Before=network-pre.target`,
  `Wants=network-pre.target`. Применяет **last-good** из `/var/lib/vnm/` (без сети,
  без скачиваний). Так же упорядочен штатный `nftables.service` — это стандартное место
  для правил, которые должны встать раньше сети. Всё, что поднимает сервисы и выходы (в
  парке — Docker; интерфейс выхода поднимает сам агент), стартует после `network-pre` и этим уже упорядочено:
  называть их в юнитах агенту не нужно.
- **`vnm-agent.service`** — `After=network-online.target vnm-boot.service`,
  `Requires=vnm-boot.service`, `Type=notify`, `Restart=always`. Сверка, здоровье, списки.

Требование «нет окна» проверяется тестом ребута (tests.md), а не выводится из `Before=`.
Пока выход поднимается после загрузки, соединения к назначениям политики получают быстрый отказ
(`unreachable`) — это I-2, отдельный приёмочный тест.

### 7.3. Сверка, блокировки, битый конфиг

- Сверка раз в 60 с и по событиям netlink (появился/пропал интерфейс выхода или любой интерфейс — для `listen_ports`/аплинка). Только
  собственные объекты (§6.1).
- **Блокировка:** все изменяющие операции CLI и агента берут `flock` на
  `/run/vnm/state.lock`. CLI ждёт до 30 с, потом отказывает.
- **Битый конфиг:** ничего не применяется частично, работает last-good, агент пишет
  ERROR и метрику `vnm_config_valid 0`; CLI возвращает ненулевой код. `version`
  конфига обязателен; неизвестная версия = битый конфиг. Миграции — командой
  `vnm config migrate`, не молча при чтении.

### 7.4. Списки

- Раз в сутки со случайным сдвигом до 6 ч. HTTPS; сверка с `<файл>.sha256sum`, который
  Loyalsoldier публикует рядом с каждым файлом (то же соглашение для `url:`-источников);
  загрузка во временный файл, атомарная подмена. Если сумма и файл взяты из разных
  релизов (выпуск между двумя запросами), сверка не сходится — старая копия остаётся,
  следующий заход скачает согласованную пару.
- Sanity-чеки перед применением: разбор protobuf успешен; для `geoip:ru` —
  **≥ 5 000 и ≤ 100 000 префиксов**; изменение числа записей относительно текущего
  **≤ 50 %**. Не прошло → старый список остаётся, WARN + метрика. Урок `update.sh`: guard
  по одному размеру молча отвергает легитимный файл и пропускает HTML-страницу ошибки.
- Старый список действует всегда, пока новый не прошёл проверки. Возраст списка:
  **> 3 суток — warning, > 7 суток — critical** (алерт).

### 7.5. Логи и метрики

- Журнал — `journalctl -u vnm-agent`, уровни ERROR/WARN/INFO/DEBUG. Логируются события,
  **не соединения**: смена здоровья WARP, снятие/возврат маршрута, применение и откат
  состояния, дрейф своих объектов, конфликт с чужими, результат обновления списков,
  ошибки резолвера. Пакетный уровень — только nft-счётчики.
- Метрики (textfile для node_exporter → Prometheus → alertmanager);
  метки только с ограниченным набором значений (имя списка, действие), без адресов:
  `vnm_policy_decisions_total{list,action}` (action: exit/block/direct/fallback),
  `vnm_policy_would_total{list,action}` (режим observe),
  `vnm_policy_listen_port_bypass_total`, `vnm_warp_healthy`,
  `vnm_warp_handshake_age_seconds`, `vnm_state_generation`, `vnm_apply_errors_total`,
  `vnm_drift_total`, `vnm_foreign_conflict`, `vnm_config_valid`,
  `vnm_list_entries{list}`, `vnm_list_age_seconds{list}`, `vnm_dns_set_entries`,
  `vnm_last_reconcile_timestamp`.

## 8. Режимы и CLI

Режимы политики:
- **`observe`** — метки и счётчики ставятся, маршруты не меняются. Счётчики считают, **что
  было бы**: `would{action=exit}`, `would{action=block}` (WARP мёртв в этот момент),
  `would{action=direct}`. Это ответ на гипотезу §0 и оценка списков. **Исключение — DNS:**
  при доменных списках он и в observe перенаправляется на резолвер (§5), иначе доменные
  наборы не наполнятся и счётчики по ним ничего не покажут; ответы те же, меняется только
  путь запроса.
- **`enforce`** — рабочий режим. Соединения, открытые до перехода (в observe или до смены
  списков), идут прежним путём до конца — как F-12: перенос живого соединения на другой
  адрес источника его рвёт. Новые соединения идут по новому режиму; долгий UDP-поток с
  keepalive останется прямым, пока не прервётся.
- **`off`** — политика снята. Снимает I-1 → требует `-allow-leak` (как и любой уход из
  `enforce`). Guard (docs/vpn-node-manager-guard-tz.md) от `off` не зависит.

Опасные операции — с автооткатом, как SSH-хардненинг:
- Любой уход из `enforce` (в `observe` или `off`) и любой переход в `off` — только с
  `-allow-leak`.
- `vnm egress enforce -auto-rollback 5m` — через 5 мин вернёт предыдущий режим, если
  не выполнено `vnm egress confirm` (из **новой** SSH-сессии). Пока переключение не
  подтверждено и не откачено, следующее запрещено. Прежний файл лежит в `/run/vnm`, как и
  таймер: ребут снимает оба, режим остаётся новым.
- `vnm egress rollback` — вернуть файл политики, который заменило временное переключение.
- `egress` меняет в `config.yaml` только значение `mode` (остальной файл байт в байт) и
  ждёт, пока агент применит режим.
- `vnm uninstall` — снимает egress/dns; без `--allow-leak` отказывается, если политика
  в `enforce` (переход RU → напрямую без явного согласия запрещён). `--keep-policy`
  оставляет правила в ядре и снимает только агент.

```
vnm install [-license KEY] [-skip-base]    vnm status
vnm base apply|confirm                     vnm doctor
vnm warp install|plus KEY                  vnm test <ip|домен>
vnm egress observe|enforce|off [-allow-leak] [-auto-rollback 5m] | confirm | rollback
vnm lists update
```

- `status` — что агент видел на последнем проходе (`/var/lib/vnm/status.json`, пишется
  рядом с метриками): режим, выходы, резолвер, списки, счётчики, «агент завис», если проход
  старше минуты.
- `doctor` — конфиг, юниты, ядро против last-good, выходы, резолвер, возраст списков
  (3/7 суток), `FORWARD = DROP`; при FAIL код возврата ненулевой.
- `lists update` — скачать источники сейчас; агент замечает новые копии сам на следующем
  проходе.
- Не сделано (не нужно пилоту): `warp status` (есть в `status`), `config migrate` (версия
  одна), `uninstall`, `--port/--proto` у `test` (решение от порта не зависит).

`vnm test` показывает решение целиком, без отправки трафика: порядок решений — из
применённого состояния, членство в наборах и здоровье — из живого ядра. Домен резолвится
как у процессов хоста, то есть через резолвер `vnm` — заодно попадает в доменные наборы.

```
$ vnm test ya.ru
ya.ru: 77.88.55.242, 2a02:6b8::2:242
77.88.55.242     ru_ip (ru_ip_4), ru_domain (ru_domain_d4)  ⇒ EXIT dev warp (mark 0xca6c, table 51820)
2a02:6b8::2:242  ru_ip (ru_ip_6), ru_domain (ru_domain_d6)  ⇒ BLOCK
```
