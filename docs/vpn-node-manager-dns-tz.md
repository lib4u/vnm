# ТЗ: свой резолвер vnm вместо dnsmasq

Дополняет §5 основного ТЗ (`vpn-node-manager-tz.md`). Меняется только **кто** отвечает на
перенаправленный DNS и кладёт адреса в наборы; перенаправление в nft, набор `dns_ports`,
«резолвер умер — DNS идёт мимо», исключение upstream-запросов резолвера — как были.

## 1. Зачем

Доменные списки держались на `dnsmasq ≥ 2.87` со сборкой `nftset`. Это привязка к ОС:

| ОС | dnsmasq | доменные списки |
|---|---|---|
| Ubuntu 24.04 / 26.04 | 2.90+, nftset | работают |
| Ubuntu 22.04 | 2.86/2.91, собран `no-nftset` | нет |
| AlmaLinux 9 | 2.85 | нет |

На 5 из 11 нод парка AWG/TT-клиенты ходят на RU-домены с зарубежных IP напрямую. Цель —
доменная часть политики работает везде, где работает vnm: нужно только ядро с nf_tables.

## 2. Решение

Резолвер — часть бинаря vnm: `vnm dns serve`, юнит тот же `vnm-dns.service`. Пакет
dnsmasq больше не ставится и не нужен.

**Отдельный процесс, а не горутина агента:**
- рестарт или обновление агента не рвёт DNS хоста и клиентов;
- исключение upstream-запросов по `meta skuid` остаётся точным: у резолвера свой
  пользователь, а агент работает от root, и исключить root = исключить весь хост;
- разбор пакетов из сети — в процессе без root: системный пользователь `vnm-dns`, из
  привилегий только `CAP_NET_ADMIN` (запись в nft-наборы; у dnsmasq было так же).

## 3. Поведение

### 3.1. Приём запросов
- UDP и TCP на `dns.port` (по умолчанию 5353), IPv4 `0.0.0.0` и IPv6 `[::]`; нет IPv6 на
  хосте — работает на IPv4, это не ошибка.
- Ответ по UDP уходит **с того адреса, на который пришёл запрос** (`IP_PKTINFO`): после
  `redirect` это адрес входного интерфейса, conntrack сопоставит ответ только с ним.
- **Не открытый резолвер**, и без таблицы vnm тоже: запрос, пришедший с аплинка (UDP — по
  индексу входного интерфейса, TCP — по локальному адресу на аплинке), отбрасывается.
  Это дублирует `dns_guard` в nft (как `except-interface` у dnsmasq): таблицы может не
  быть, а порт слушается.
- Защита памяти: не больше 1024 запросов одновременно по UDP и 256 TCP-соединений;
  сверх — UDP-запрос отбрасывается (клиент повторит), TCP-соединение закрывается. У TCP
  таймаут простоя 10 с.

### 3.2. Ответ
- `version.bind CH TXT` — отвечает сам, без upstream'ов («vnm»): по нему агент проверяет,
  что резолвер жив (проба не меняется). Остальные запросы класса CH — REFUSED.
- Не QUERY (UPDATE, NOTIFY…) — NOTIMP. Непарсящийся пакет — отбрасывается.
- Остальное пересылается в `dns.upstreams` как есть (EDNS, DO/CD сохраняются) с новым
  случайным ID; клиенту — с его ID.
- Upstream'ы по порядку, первым идёт тот, что ответил последним. Попытка — 2 с; таймаут,
  сетевая ошибка, SERVFAIL или REFUSED — следующий upstream. Общий бюджет запроса 5 с.
  Никто не ответил — SERVFAIL.
- UDP-ответ upstream'а с TC — повтор у того же upstream'а по TCP. Ответ длиннее, чем
  принимает клиент по UDP (512 или размер из EDNS), обрезается с TC — клиент придёт по TCP.
- **Кэша нет** (решение). Upstream'ы — в том же ДЦ (1–5 мс), а без кэша каждый ответ
  проходит через наполнение наборов с настоящими TTL. У хоста свой кэш в
  systemd-resolved, у клиентов — в их ОС.

### 3.3. Наполнение наборов — до ответа клиенту
- Только ответы NOERROR. Имена ответа: имя запроса, владельцы записей Answer и цели
  CNAME. Если хоть одно имя совпало со списком — **все** A/AAAA из Answer и подсказки
  `ipv4hint`/`ipv6hint` записей HTTPS/SVCB идут в наборы этого списка (`Set4`/`Set6`).
- Совпадение — по суффиксу, как у `nftset` dnsmasq: запись `example.ru` покрывает
  `example.ru` и все его поддомены. Регистр не важен.
- Все адреса ответа добавляются **одной транзакцией netlink**, и только потом ответ уходит
  клиенту. Не получилось — клиент получает **SERVFAIL**, а не адрес: адрес, которого нет в
  наборе, ушёл бы с IP ноды (I-1 для доменной части).
- Записи без таймаута и переживают замену таблицы — как в §5 основного ТЗ. Повторное
  добавление существующего адреса — не ошибка: адрес добавляется на каждый ответ, в том
  числе после пересоздания набора.

### 3.3a. Без IPv6 для списков, уходящих в выход
Выходы пока только IPv4 (§3.5 основного ТЗ): IPv6 назначений из списка с действием
`exit` блокируется. Клиент с IPv6, получивший AAAA RU-сайта, упирается в «unreachable»
(найдено на одной из нод 27.09.2026). Поэтому в enforce ответы по доменам таких списков
отдаются **без IPv6**: AAAA и их RRSIG убираются, у HTTPS/SVCB — `ipv6hint`. Запрос AAAA
получает пустой NOERROR, клиент идёт по IPv4 — через выход. В observe ответы не
меняются. Снимается, когда выходы получат IPv6.

### 3.4. Конфиг
Агент пишет `/var/lib/vnm/dns/resolver.json` и перезапускает юнит, когда конфиг меняется
(как было с dnsmasq). Резолвер читает конфиг при старте. Содержимое: порт, upstream'ы,
аплинки, семейство и имя таблицы, наборы с доменами. Имена наборов — ядерные: резолвер не
знает правил именования таблицы.

Нет доменных списков — конфига нет, юнит не работает (`ConditionPathExists`), как было.

### 3.5. Юнит
```
User=vnm-dns
StandardInput=file:<state>/dns/resolver.json   # открывает systemd от root
ExecStart=<binary> dns serve -config -
AmbientCapabilities=CAP_NET_ADMIN
CapabilityBoundingSet=CAP_NET_ADMIN
NoNewPrivileges, ProtectSystem=strict, ProtectHome, PrivateTmp
Restart=always, RestartSec=2
```

## 4. Установка и переход

- **Порт резолвера в фаерволе хоста.** Перенаправленный DNS доставляется локально, и
  ufw/firewalld с «запрещено всё, что не разрешено» его отбрасывает: у клиентов туннеля
  пропадает DNS целиком (найдено на пилотной ноде 27.09.2026, было и с dnsmasq; затронуты все ноды
  с ufw). Установщик открывает `dns.port` (TCP и UDP) в активном ufw или firewalld; на
  аплинке порт закрыт таблицей vnm (`dns_guard`) и самим резолвером. `doctor` — FAIL,
  если при доменных списках фаервол порт не пускает. Прочие фаерволы — на операторе.
- Установщик создаёт системного пользователя `vnm-dns` (без дома, `nologin`) всегда, а не
  только при доменных списках: списки могут добавить в конфиг позже без переустановки.
- `dnsmasq-base` больше не ставится; проверка `nftset` и предупреждение «dnsmasq без
  nftset» уходят. Уже стоящий пакет не удаляется: vnm его не ставил на всех нодах и не
  знает, кто им ещё пользуется.
- Переход на ноде с dnsmasq (`vnm install -skip-base` новым бинарём): установщик
  переписывает юнит и удаляет старый `dns/dnsmasq.conf`, dnsmasq продолжает работать до
  рестарта агента. Новый агент первым проходом ставит `skuid` пользователя `vnm-dns`, пишет
  `resolver.json` и перезапускает юнит — уже со своим резолвером. Окно, в котором старый
  dnsmasq спрашивает сам себя, — миллисекунды между заменой таблицы и рестартом юнита.
  Наборы при этом не теряются (таблица не удаляется).
- На нодах только с `ru_ip` (22.04, AlmaLinux) доменные списки включаются правкой конфига
  (`lists: [ru_ip, ru_domain, ru_suffix]`) — после обновления бинаря.

## 5. Проверка

**Тесты (без root):**
- совпадение по суффиксу, регистр, цепочки CNAME, HTTPS-подсказки;
- ответ не уходит, пока наборы не записаны; ошибка записи → SERVFAIL;
- перебор upstream'ов, повтор по TCP при TC, обрезка ответа под размер клиента;
- `version.bind`, CH, не QUERY, мусор;
- запрос с аплинка отброшен.

**Стенд (netns, root):** настоящий `nft` с наборами; запрос через `redirect` → адрес в
наборе → ответ приходит с адреса перенаправления.

**Нода A (Ubuntu 24.04, до этого dnsmasq):**
- переход с dnsmasq без потери наборов: число элементов до и после;
- `nplus1.ru/cdn-cgi/trace` с хоста и из AWG идёт через WARP;
- `meduza.io` — напрямую;
- `vnm status` и `doctor` зелёные;
- резолвер не отвечает на аплинке, в том числе без таблицы vnm.

**Нода B (Ubuntu 24.04, ядро без `nft_objref`):**
- то же на урезанном ядре;
- затем включить домены на одной ноде 22.04 или AlmaLinux — по команде владельца.
