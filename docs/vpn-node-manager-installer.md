# vpn-node-manager — установщик: base и WARP

Часть ТЗ **docs/vpn-node-manager-tz.md** (роль «установщик», §2 ТЗ). Приёмочные тесты —
docs/vpn-node-manager-tests.md. Ссылки «ТЗ §N» — на основной документ.

## 1. Модуль `base`

- **SSH:** `/etc/ssh/sshd_config.d/00-hardening.conf` (`PasswordAuthentication no`,
  `KbdInteractiveAuthentication no`, `PermitRootLogin prohibit-password`); `00-`
  обязателен — `50-cloud-init.conf` включает пароль, а у sshd побеждает первое значение.
  Нет ни одного ключа в `authorized_keys` → отказ; ключ с `command=` (заглушка
  cloud-init «Please login as the user ubuntu» на root) ключом не считается. SSH —
  последний шаг `base`: таймер автоотката 5 мин взводится после apt, иначе ожидание
  dpkg-lock съедает окно. `vnm base confirm` принимается, только пока откат ожидает, и
  только из другой SSH-сессии: `$SSH_CONNECTION` применившей сессии записан в
  state-каталог. Не удалось взвести откат или перезагрузить sshd → drop-in удаляется,
  чтобы неподтверждённое не включилось при ребуте.
- **fail2ban:** jail `sshd`, `backend = systemd`, `maxretry 4`, `findtime 10m`,
  `bantime 1h` с удвоением до `1w`. `ignoreip`: адреса управления + подсети туннелей
  (`10.77.0.0/16`): SSH изнутри VPN приходит с адреса туннеля, бан по нему бессмыслен.
- **sysctl** — таблица с обоснованием:

| Параметр | Значение | Зачем | Риск |
|---|---|---|---|
| `tcp_congestion_control` / `default_qdisc` | bbr / fq | скорость на лоссовых путях до РФ | нет |
| `tcp_slow_start_after_idle` | 0 | длинные клиентские сессии не сбрасывают окно | нет |
| `tcp_mtu_probing` | 1 | PMTU-дыры на сотовых | нет |
| `rmem_max`/`wmem_max` | 64 МБ | QUIC/hysteria, UDP-всплески | память на 1 ГБ-нодах — только потолок |
| `tcp_rmem`/`tcp_wmem` max | 32 / 16 МБ | BDP на 150 мс RTT | то же |
| `nf_conntrack_max` / `buckets` | 262144 / 65536 | 7680 по умолчанию на 1 ГБ → «443 отвечает через раз» | ~80 МБ при заполнении |
| `nf_conntrack_tcp_timeout_established` | 600 | обрывы без FIN за ТСПУ держали записи 5 суток | согласовано с `connIdle=180` Xray |

- **swap:** ОЗУ < 2 ГБ и swap < 1 ГБ → swapfile 2 ГБ.
- **apt:** все операции ждут `dpkg`-lock до 15 мин с понятным сообщением
  (unattended-upgrades на свежей Ubuntu держит его ~10 мин).

## 2. WARP

Своя реализация, **без wtm**. wtm решает больше, чем нам нужно (Tor, меню, сниппеты
Xray, самообновление — 4 тыс. строк bash), а главное — ставит свой watchdog, то есть второй
контроллер интерфейса рядом с агентом (ТЗ §4). Из него взяты только проверенные решения
(перечислены ниже как требования).

Что берём как есть: бинарь **`wgcf`**, пин версии + sha256, лежит в
`/usr/local/lib/vnm/wgcf`. Протокол регистрации Cloudflare меняется именно там; наш код
при таком изменении максимум обновляет пин.

`vnm warp install [--license <KEY>]`:
1. **Регистрация:** `wgcf register --accept-tos --config /etc/vnm/exits/warp/wgcf-account.toml`,
   до 3 попыток с паузой 10/30/60 с на 5xx и сетевые ошибки. Путь к аккаунту — только
   флагом `--config`: переменную `WGCF_ACCOUNT` новые версии wgcf игнорируют.
2. **WARP+** (если дан ключ): вписать `license_key` в аккаунт → `wgcf update --config …`
   на то же устройство, без перерегистрации; `wgcf status` → тип аккаунта. Остался
   `free`/`limited` или `wgcf update` отказал — WARN и продолжаем на бесплатном (у
   потребительских ключей лимит устройств, Cloudflare ограничивает их применение к
   wgcf); при отказе аккаунт возвращается к прежнему содержимому. Ключ в выводе
   маскируется.
3. **Конфиг:** `wgcf generate` во временный файл → собрать **свой** `warp.conf` в формате
   ТЗ §4: только IPv4-адрес, `AllowedIPs = 0.0.0.0/0` (без `::/0` — IPv6 в MVP блокируется,
   ТЗ §3.5), `MTU = 1280`, `PersistentKeepalive = 25`, без `DNS`/`Table`/`PostUp`.
   `Endpoint` — IP, а не `engage.cloudflareclient.com`: иначе подъём выхода после ребута
   зависит от DNS. Список запасных `endpoints` — в конфиг агента.
4. Права 600 на аккаунт и `warp.conf` (там `access_token`, `license_key`, приватный ключ).
5. Сигнал агенту на пересчёт состояния → агент поднимает интерфейс и проверяет здоровье
   (ТЗ §4); `vnm warp install` ждёт первого «здоров» до 60 с и печатает результат.

`reserved` не вычисляем: он нужен только встроенному wireguard-outbound Xray, а здесь
интерфейс ядра.

`vnm warp plus <KEY>` — WARP+ на существующей регистрации (шаг 2 выше).
`vnm warp reregister` — новая регистрация (новая личность выхода) с подтверждением; на
время — правило 1001 (RU-назначения отказывают).

- Одна регистрация на ноду: общий ключ на несколько нод перебивает сессии (Cloudflare
  держит сессию за последним endpoint'ом).
- Регистрация не удалась → нода остаётся с `unreachable` (RU заблокирован, не течёт),
  `vnm status` это показывает. Корректное состояние, не ошибка установки.

### 2.1. Миграция с существующего WARP

**Любой существующий WARP сносится** — ручной и wtm, если где-то стоит. Ручные
установки хрупкие: свой `PostUp` с `ip rule`/маршрутами (чужой владелец объектов агента),
разные версии wgcf, неизвестные довески (таблицы 51821/51822 на одной из нод). wtm — второй
контроллер. Единообразие парка важнее сохранения регистрации.

Признаки: юнит `wg-quick@warp`; файлы wtm (`/opt/wtm/`, `/usr/local/bin/wtm`,
`/etc/cron.d/wtm-warp-watchdog`, `/etc/wireguard/warp-*-outbound.json`); `PostUp`/`PreDown`
в `/etc/wireguard/warp.conf`; `ip rule` с меткой 0xca6c в диапазоне 1000–1009, не
созданные `vnm`. Снос необратим, поэтому `wgcf` скачивается до него: без инструмента
замены старый WARP остаётся. Процедура — fail-closed на каждом шаге:

1. **Инвентаризация и бэкап**: `ip rule`, все таблицы, на которые ссылаются правила с
   метками 0xca6c–0xca6f, `/etc/wireguard/*`, юниты и drop-in'ы `wg-quick@warp`, файлы
   wtm → `/var/lib/vnm/migration/<дата>/`. Правило, которое `vnm` не может однозначно
   отнести к существующему WARP (как `0xca6d → 51821` на одной из нод), — **стоп**: отказ с
   описанием, решение за оператором.
2. **Захват блокировки**: поставить свои правила `1001 fwmark 0xca6c unreachable` и
   `1000 fwmark 0xca6c lookup 51820` (пока старые ещё стоят — дубли допустимы), затем
   удалить старые. С этого момента метка 51820 без маршрута = отказ, а не прямой выход.
3. **Снос**: сначала watchdog wtm (cron), потом `systemctl disable --now wg-quick@warp` →
   маршрут в 51820 исчезает → RU-трафик (в том числе Xray с `sockopt.mark`) получает быстрый
   отказ. Удалить конфиги, аккаунты wgcf, drop-in'ы, wtm и ручные скрипты (из бэкапа их
   можно вернуть).
4. **`vnm warp install`** — новая регистрация, интерфейс поднимает агент.
5. **Проверка здоровья** (ТЗ §4) → агент ставит маршрут → RU снова через WARP.

Окно отказа RU-назначений = время шагов 3–5 (ориентир — 1–2 мин). Это ожидаемое
поведение (I-2), не простой: зарубежный трафик и управление не затрагиваются.
Откат — из бэкапа шага 1 (`vnm warp restore-legacy <дата>`), только руками.
